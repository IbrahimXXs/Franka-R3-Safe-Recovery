# Detector v2 development

Run `./productivity_detector_v2.sh --headless`. Default output: `outputs/Contact-Productivity-DetectorV2-Dev`; existing directories are refused. This collects 80 new nominal trajectories, freezes calibration, then compares v1/v2 on the same 80 conditions (240 episodes total, roughly 3–4 hours). Native 120 Hz FORGE, assets, physics, hard safety, recovery timing and command budgets remain unchanged.

The 80 targeted paths include moderate successful controls, terminal-depth conditions, severe oblique tilts, severe combined offset/tilt and late steep ramps. These are targeted inputs, not guaranteed outcome labels. Four signed/onset groups per family each have four magnitude levels. Before collection, 15 whole groups / 60 conditions are assigned to calibration and five groups / 20 conditions to development validation. Shared sign/onset magnitude variants never cross this split. All paths begin aligned; no window-level train/test split or ML is used.

Normal eta `< 0.4212659765112803` for two adjacent checks is unchanged. The terminal branch requires 0.5 s entirely in endpoint hold, measured depth below success and above contact onset, a single segment and a small measured depth range divided by window duration. Using the range prevents oscillations with zero net progress from masquerading as stagnation. The urgent branch requires original positive-command insertion eligibility, extremely low eta, positive deficit rate `(command progress - actual progress)/0.5 s`, and a rapid increase in that rate between adjacent 0.1 s checks. No normal load enters either branch. Resets, gaps and recovery phases invalidate urgent history.

The fixed candidate grid is in the development plan. Calibration maximizes new/earlier safe coverage of unsuccessful nominal trajectories with zero additional alerts on successful calibration trajectories. It does not optimize closed-loop success. Thresholds are frozen before any v1/v2 comparison run; validation and comparison outcomes cannot change the selected configuration. Nominal successful-trajectory alerts are the main false-trigger measure. Closed-loop interventions on paired nominal successes are an additional, imperfect counterfactual proxy; prefix matching and reset differences are reported.

Recovery is reused via the exact existing `execute_dewedge` code object with private detector and logging dependencies. Its module and all recovery helpers remain byte-identical; no global monkeypatch is used. The new Stream columns only annotate detector decisions. Both policies keep all safety gates, actual 0.5 mm retreat verification/dwell, measured neutral-pose retry and two-recovery cap. Audit replays the original recovery implementation and checks every detector decision.

The prior 48-condition benchmark is excluded from calibration and evaluation. Only its pre-collection parameter plan is read to reject duplicate paths. Previous outcomes motivate the requested design, but are never calibration samples. This experiment is development only; no final generalization evaluation is launched.

Outputs: report.md, detector_v2_config.json, summary.csv, trigger_analysis.csv, false_trigger_analysis.csv, calibration_candidates.csv, validation.json, policy and failure tables, per-run logs/events, plots, development plan and source snapshots. Report regeneration is offline: `python -m research.productivity_detector_v2_report outputs/Contact-Productivity-DetectorV2-Dev`.
